# MAHA Bhulekh 7/12 Bulk Downloader
## Project Documentation

### 1. Objective
This project is an educational/assignment proof-of-concept for downloading 7/12 public-view outputs from the Maharashtra Bhulekh portal. The workflow is:
- User selects Division → District → Taluka → Village.
- Application discovers available Survey/Gat/Hissa records.
- Records are processed and 7/12 public-view outputs are saved locally.
- CSV/Excel reports are generated.

### 2. Technical Approach
The application utilizes a robust architecture for controlled web scraping and processing:
- FastAPI backend for handling API requests and application logic.
- Playwright browser automation for interacting with the portal.
- SQLite persistence for maintaining job state and record tracking.
- HTML/CSS/JavaScript frontend for the user interface.
- Location selection, survey/gat discovery, and a persistent job/record queue.
- Sequential/controlled processing of records.
- PDF capture/output of the 7/12 records.
- CSV/Excel reporting for summary and tracking.
- Live progress reporting via the frontend.

Output structure is organized as:
`output/<District>/<Taluka>/<Village>/`

### 3. CAPTCHA & Human Verification Strategy
This application is designed to operate ethically and transparently:
- CAPTCHA is NOT cracked, bypassed, OCR'd, solved automatically, replayed, or stored.
- Mobile number and CAPTCHA are manually entered by the operator in the official visible Bhulekh browser window.
- Automation waits for a successful portal result.
- After successful verification, the application captures the record and continues processing.
- The same browser context/session is preserved where possible to reduce redundant verification.
- The application does NOT guarantee that one CAPTCHA works for all records.
- Portal/session resets can require verification again.
- Mobile number and CAPTCHA values are not intentionally persisted by the application.

**Test Mobile Number Note:** The assignment provided `1234567890` as a test number. During live testing, this number did not complete the portal's verification flow, so a valid mobile number was entered manually when required by the official portal. The application does not intentionally capture, log, or persist the entered mobile number.

### 4. Reliability & Recovery
The application implements several mechanisms to ensure reliability:
- Pause/resume functionality for long-running jobs.
- Ability to retry failed records.
- Persisted SQLite state to track progress across restarts.
- Restart/crash recovery where implemented.
- Bounded retry/backoff for network requests.
- Navigation timeout handling.
- ASP.NET postback synchronization to ensure page elements are ready.
- Portal/session reset detection to prompt for re-verification.
- Visible-browser/window checks for human interaction.
- Error categorization to distinguish between transient network errors and persistent portal issues.
- Controlled request rate / polite processing to avoid overwhelming the server.

### 5. Performance
Performance is heavily dependent on the Bhulekh portal's response time and the operator's speed during human verification.

Observed performance benchmark:
- Sample processed records: 5
- Observed end-to-end time: approximately 2–3 minutes
- Approximate end-to-end time per processed record: 24–36 seconds

Important Notes:
- This includes manual CAPTCHA/human verification, portal response time, and network delay.
- It is NOT guaranteed throughput.
- Automated Processing Seconds and Human Verification Seconds are recorded separately in CSV/Excel reports.
- Performance depends heavily on Bhulekh portal response and operator verification speed.

### 6. Sample Output
Sample output generated by the application is included under:
`sample_output/PDFs/`

The sample contains selected successfully generated PDFs from one village together with CSV/Excel reporting.
Important: The sample report may contain PENDING records because only a subset of the discovered village records was processed for the demonstration. It is not a complete village download.

**Target Village Note:** The requested target flow Pune → Maval → Shivali was tested and resulted in 700+ discovered records. Because the official portal requires human verification and verification may be required repeatedly during processing, completing the entire 700+ record village solely for the submitted sample would require substantial manual interaction. Therefore, a smaller demonstration village/sample was used for the submitted sample output. The same application workflow is used for discovery, processing, PDF generation, progress tracking, and CSV/Excel reporting.

### 7. Official API / Bulk Access Research
Based on research documented in `docs/api-and-bulk-access.md`:
- No documented open public bulk-download API suitable for this assignment was identified in the official resources reviewed.
- Official Maharashtra material indicates API-based Record of Rights access exists for certain institutional users.
- Therefore this proof-of-concept uses controlled UI automation with human verification.
For details, refer to `docs/api-and-bulk-access.md`.

### 8. Limitations
- CAPTCHA/mobile verification remains human-in-the-loop.
- Portal session/verification may reset between records.
- Portal/network performance is outside application control.
- UI/layout changes on the official portal may require selector updates.
- Numeric Survey/Gat discovery is the verified automation path.
- Akshar/अक्षरी enumeration remains unverified.
- Public Mahabhulekh viewing output must not be represented as the separate legally valid Digitally Signed 7/12 service.
- Large villages can take significant time because human verification may be required repeatedly.

**Digital Signing:** Digitally signed 7/12 documents were explicitly outside the scope of the assignment. This project works with the public-view Bhulekh workflow and does not implement digital signing.
